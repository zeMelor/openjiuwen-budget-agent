# openJiuwen budget agent

Харнесс кодового агента на базе [openJiuwen](https://pypi.org/project/openjiuwen/) 0.1.19 для openJiuwen
Challenge 2026. Он получает каталог из 100 задач (coding, search, math, data_analysis) и за фиксированный бюджет
токенов набирает как можно больше баллов.

Главная идея: выходной токен в 10 раз дороже входного, поэтому всю детерминированную работу делает харнесс без
токенов. Он сам гоняет тесты, собирает нужные карточки из базы знаний и запускает код. Модель только пишет то, что
без неё не написать: исправление функции, короткую программу или ответ. Все вызовы модели идут через `ReActAgent`
openJiuwen, а учёт токенов, лимиты и остановки сделаны рейлами (`AgentRail`).

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

**Важно: папка с задачами должна быть открыта на запись.** Агент сохраняет ответ в файл `answer.txt` в папке
каждой задачи, а в задачах coding ещё и исправляет код в этой папке. Если у папки с задачами другой владелец и
обычные права 755, контейнер не сможет туда ничего записать, и ответы не сохранятся. Изнутри контейнера это не исправить: с `--cap-drop ALL` у него нет прав менять чужие папки.

Перед запуском достаточно сделать одно из двух (оба способа проверены, на примерах 20 из 20):

```bash
# 1) открыть папку с задачами на запись — так же, как уже делается chmod 777 "$OUT"
chmod -R a+rwX "$TASKS"

# 2) или запустить контейнер от владельца папки: добавить к docker run
--user "$(id -u):$(id -g)"
```

Если папка всё же закрыта, агент не падает. В начале журнала будет предупреждение, а ответы всё равно найдутся:
в `OUT`, если он подключён (см. ниже), и в последней строке журнала `answers: {...}`. Задачи coding в такой папке
решить нельзя: исправленный код некуда сохранить.

- **Сборка** с нуля (`--no-cache --pull`) занимает 128 с при лимите 1000 с, образ весит 1,43 ГБ (лимит 4 ГБ). Все версии
  зафиксированы: базовый образ `python:3.11.9-slim-bookworm`, пакеты в `requirements.lock` (зависимости
  openJiuwen и pytest: тесты coding-задач могут его импортировать). При запуске ничего не
  скачивается.
- **Ответ** пишется в `answer.txt` каталога задачи сразу после её решения (и копией в `workspace/`, если он есть).
  Если прогон убьют, решённое останется. Для coding ответ `DONE`, код исправлен на месте.
- **`OUT`** (необязательно): файл или существующий каталог. Туда после каждой задачи пишется сводка всех ответов
  `{task_id: answer}` (в каталоге — `solutions.json`), а в каталог ещё и `<каталог задачи>/answer.txt`: запасная
  копия ответов на случай, если каталог задач закрыт на запись.
- **Параметры запуска** разбираются терпимо: незнакомый параметр не роняет прогон, а пишется в журнал; файл решений
  узнаётся и как `--output`, `-o`, `--answers-file` и т. п.; без `--tasks-dir` каталог задач берётся из `TASKS` или
  `/data/tasks`; бюджет — `--budget` (можно `100k`), иначе `BUDGET`.
- **Логи** пишутся в `/tmp/budget_agent_runs/<время>/` (или в `--log-dir`), их формат описан ниже в разделе
  «Траектории».
- **Время:** 100 задач gen-s1 прошли за 104 с при 2 задачах параллельно (по умолчанию 3). После 3300 с новые задачи не берутся,
  таймаут одной задачи 240 с, одного вызова модели 120 с (у моделей с рассуждениями он растёт с потолком ответа:
  2 500 токенов — 197 с). После таймаута вызов повторяется один раз: оборванный запрос прокси всё равно
  досчитывает и оплачивает, а харнесс его расхода не видит.

Необязательные настройки:

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `TOKEN_BUDGET` или `BUDGET` (или `--budget`) | 100000 | сколько токенов харнесс готов потратить |
| `PARALLEL` (или `--parallel`) | 3 | задач одновременно |
| `MODEL` (или `--model`) | `qwen3.8-27b-noreason` | модель |
| `SECOND_PASS=0` (или `--no-second-pass`) | включён | второй проход: перепроверка сомнительных ответов из излишка бюджета |
| `COMPUTE_PLAIN_VERIFY=1` | выключен | вернуть перепроверки math/data с готовым ответом без сигналов сомнения; проверки coding и подозрительных ответов включены независимо от этой настройки |
| `LLM_RPM` | 50 | не больше стольких запросов к модели за любые 60 с (в памятке тарифа — до 60 в минуту); 0 — без ограничения |
| `MATH_MOTION=0` | включён | выключить извлечение исходных данных для встречи/догоняния в минутах; обычный Python-решатель остаётся запасным путём |
| `LLM_TIMEOUT_S` | 120 | таймаут одного вызова модели, секунд |
| `PRECHECK_SOFT_SKIP=1` | выключен | пропускать задачу, если значение, имя или файл из условия не найдены в её файлах (по умолчанию такая задача решается последней в очереди) |
| `UNANSWERED_RETRY=0` | включён | не давать во втором проходе попытку задачам, оставшимся без ответа |

Локально без Docker:

```bash
python3.11 -m venv .venv && .venv/bin/python -m pip install openjiuwen==0.1.19
cp .env.example .env          # вписать LLM_BASE_URL и LLM_API_KEY
.venv/bin/python run_agent.py --tasks-dir <каталог с задачами>
```

`requirements.lock` снят в базовом образе (Linux) и нужен для сборки образа. Без Docker команды модели выполняются
прямо на машине, поэтому для прогонов лучше Docker.

## Как устроено

`run_agent.py` → проверки «невыполнимо» без LLM (`precheck.py`) → порядок задач (`planner.py`) → решатель по
типу задачи (`solver.py`) → нормализация ответа (`answers.py`) → `answer.txt` → второй проход (`second.py`).

**Два прохода.** Первый решает все задачи дёшево, одним-тремя вызовами, и сразу пишет ответы. Второй
перепроверяет ответы с сигналом сомнения, тратя только излишек бюджета:
- **сигналы сомнения** считаются без токенов: ответа нет в собранных карточках, тип ответа не тот (на «сколько» не
  число), вопрос на обратный поиск или сравнение, coding застрял после прогресса;
- **второе мнение** даёт другая модель (`qwen3.6-35b-a3b-noreason`), при расхождении спор решает модель с
  рассуждениями (`qwen3.8-27b`). Застрявший coding получает модель с рассуждениями;
- **coding, прошедший видимые тесты, сверяется с docstring:** скрытые тесты проверяют поведение, которого видимые
  не касаются (None, пустой ввод, округление половин). Модель видит модули целиком и правит только противоречия
  docstring; правка остаётся, только если видимые тесты по-прежнему проходят. Сверку делает модель с рассуждениями,
  если на неё хватает излишка (иначе — без рассуждений): на регрессе на одних и тех же состояниях кода она дала
  21 -> 29 баллов из 38 против 21 -> 25;
- **ответ меняется**, только если два независимых ответа совпали против исходного или coding прошёл тесты.
  Записанный ответ не удаляется;
- **задача без ответа получает попытку.** search, math и data, у которых ответ оборвался по длине или кончился
  потолок на задачу, получают один заход модели с рассуждениями (потолок ответа 2 500); задача любого типа после
  исключения или таймаута решается заново обычным путём. Резерв для таких задач не держится: без попытки балла
  точно нет, а неверный ответ не хуже пустого.

На двух честных наборах (hold-c5, hold-c6) второй проход исправил одну задачу (+3 балла) и не испортил ни одной;
на тренировочных — ещё 6 задач. math и data без сигнала сомнения по умолчанию не перепроверяются: на двух
прогонах 12.11 эти проверки не дали баллов и потратили 5 549 токенов.
При `COMPUTE_PLAIN_VERIFY=1` возвращается прежний режим: перепроверяются задачи с наградой не ниже середины
диапазона наград набора (при наградах 1–5 это 3).

| Тип | Что делает харнесс | Что делает модель | Вызовов |
| --- | --- | --- | --- |
| coding (`coding.py`) | находит тесты и исходники при любой раскладке, сам гоняет тесты, показывает модели только упавшие тесты и нужные функции, вставляет её правку через AST, перезапускает тесты | присылает только изменённые функции | 1–3 |
| search (`search.py`) | собирает карточки базы знаний: названные в вопросе, по ссылкам между ними и обратные ссылки для вопросов «кто / сколько» | отвечает одной строкой | 1 |
| search по таблицам (`datasearch.py`) | без токенов узнаёт вопрос о таблице или конфиге базы (файл назван в вопросе; «наименьший / сумма / сколько» и поле таблицы), показывает структуру нужных файлов | пишет Python-код, харнесс его запускает | 1, при ошибке 2 |
| math, data_analysis (`compute.py`) | показывает заголовки и структуру файлов, запускает код модели, берёт последнюю строку вывода | пишет только Python-код | 1, при ошибке 2 |
| math: встреча/догоняние (`motion.py`) | для двух объектов с постоянными скоростями в км/ч находит пересечение траекторий по временным участкам; ответ в минутах | извлекает позиции, скорости, моменты старта и точку отсчёта ответа в JSON | 1; при непригодных данных — обычное решение кодом |
| остальное и откаты | `ReActAgent` с инструментом `sh` в текстовом режиме (`texttool.py`, без JSON-схемы инструмента) | ведёт поиск командами | 1–4 |

**Формат ответа и задачи берутся из условия, а не из примеров** (найдено на сторонних открытых наборах):
- просит ли условие ответ в несколько строк («one per line», «exactly 3 rows») — тогда пишется весь вывод, иначе
  последняя строка;
- какое слово писать после исправления (`DONE`, `PASS`) и что писать, если решить нельзя (`UNSOLVABLE`), — только
  если условие это называет;
- тип задачи не из регламента (`sql`, `shell`) решается по файлам: тесты → coding, `kb/` → search, данные → data;
- search ищет отличительные слова вопроса во всех файлах базы, включая скрытые, `.ics`, `.vcf`, `.ini`, `.gz` и SQLite;
- вопрос о таблице или конфиге базы (наименьший остаток, сумма, версия сервиса в `config/services.yaml`, ссылка из
  одной таблицы в другую) решается кодом, а не чтением глазами; база только из карточек этот путь не включает;
- адрес прокси без `/v1`: при старте харнесс пустым запросом (без токенов) проверяет, где у прокси маршрут
  `chat/completions`, и при необходимости дописывает `/v1`; адрес с версией не трогается;
- «Round to N decimals» в условии — ответ пишется ровно с N знаками после запятой («47701.00», «38.50»);
- бюджет берётся из `BUDGET`; если его может не хватить на первый проход (меньше 1,3 оценки), потолок расхода на
  одну задачу сжимается пропорционально, чтобы одна трудная задача не съела бюджет нескольких лёгких;
- зависшие или слишком медленные тесты (45 с) убиваются вместе с дочерними процессами, модель получает подсказку
  «алгоритм слишком медленный».

## Оценка расхода токенов

1. **Учёт.** После каждого вызова рейл `MeterRail` берёт `usage` из ответа прокси и считает
   `completion + prompt / 10`; токены рассуждений прокси включает в completion. Каждый вызов пишется в
   `calls.jsonl`.
2. **Оценка до решения.** У каждого типа задачи есть оценка стоимости (`planner.py`): средний расход первого
   прохода на наших отложенных наборах, включая невыполнимые задачи. Это math 85, search 105, data_analysis 140,
   coding 270, неизвестный тип 600.
3. **Порядок.** Задачи решаются по убыванию `reward / оценка`: если бюджет окажется меньше ожидаемого и прокси
   перестанет отвечать, самые выгодные задачи уже решены и записаны. Проверка тесным бюджетом: набор из 48 задач,
   которому нужно ~6 600, при бюджете 2 500 набрал 74 балла из 106.
4. **Отсечение.** Если остаток бюджета меньше оценки задачи, её не начинаем. У каждого типа свой потолок расхода на
   задачу (math 800, data_analysis 1 000, coding 1 200, search 1 650): безнадёжная задача не съедает бюджет.
5. **Экономия выхода.** У каждого типа свой потолок длины ответа (search 120 токенов, 400 для подсчётов; код для
   math 500 и data 600 — обычно хватает 44–68; правка coding 1024). Обрезанный ответ отправляется на один повтор. Модель не пишет команды и обёртки: код
   запускает и ответ записывает харнесс.
6. **Излишек — на перепроверку.** Места решают баллы, токены сравнивают только при равенстве баллов, поэтому
   неиспользованный бюджет идёт на второй проход. Тратится только излишек: остаток минус резерв
   `max(10 000, 0,3 × бюджет)`. Очередь строится по убыванию `reward × вероятность ошибки / стоимость
   перепроверки`; вероятности взяты из наших прошлых прогонов. Ответы первого прохода к этому моменту уже
   записаны, поэтому, если бюджет кончится раньше, решённое не пропадёт.

## Поиск невыполнимых задач

Невыполнимая задача баллов не даёт, поэтому цель — потратить на неё как можно меньше. Ответ на неё не пишем.

1. **Проверки без LLM, 0 токенов** (`precheck.py`), двух уровней.

   Жёсткие — задача отбрасывается до вызова модели:
   - видимые тесты требуют от одного и того же вызова разных результатов в разных тестах (в одном файле или в
     разных); разные ожидания внутри одного теста противоречием не считаются: между вызовами меняется состояние;
   - тест импортирует модуль, которого нет ни в файлах задачи, ни в окружении.

   Мягкие — задача решается, но последней в очереди первого прохода:
   - значение в кавычках или имя «Имя Фамилия» из условия нигде не встречается в файлах задачи;
   - условие ссылается на файл с данными, которого нет в каталоге.

   Принцип: ложное срабатывание стоит баллов, а пропуск — только токенов. Мягкие проверки — догадка о
   формулировке, а формулировки финальных задач будут другими: на переписанных условиях примеров они срабатывали
   на выполнимых задачах («write 'DONE' to answer.txt», «Find Irina Smith's…», ответ 'yes' или 'no'), а до того 2
   из 13 таких отсечений на новых наборах оказались выполнимыми задачами. Поэтому по ним задача не пропускается:
   при тесном бюджете она отпадёт первой, при свободном решается как обычная. На 567 задачах наших наборов и
   примеров ни одна выполнимая задача не отброшена и не сдвинута, 15 невыполнимых отброшены, 6 сдвинуты в конец.
2. **Отказ модели.** В промптах math, data и search модель может ответить `UNANSWERABLE`, если данных нет или они
   противоречат друг другу.
3. **Сигналы харнесса.** Код модели упал на колонке или файле, которые названы в условии, но отсутствуют в данных:
   это невыполнимая задача, повтор не нужен. coding без прогресса между попытками останавливается досрочно.

На gen-s1 20 невыполнимых задач стоили 818 токенов (12 % расхода; замер v8.6, когда мягкие проверки ещё
отбрасывали задачу). Все 7 coding отброшены проверками без единого вызова, остальным хватило одного вызова. На 5 из
20 модель невыполнимость не распознала и ответ всё же записан.

## Траектории

[trajectories/gen-s1/](trajectories/gen-s1/): прогон v8.6 (до второго прохода) на 100 задачах набора gen-s1
(из них 20 невыполнимых) в контейнере с флагами организаторов, через локальный прокси, который считает бюджет так
же, как прокси организаторов. Во втором проходе строки `results.jsonl` помечены `"pass": 2`.

| Файл | Что внутри |
| --- | --- |
| `harness.log` | ход прогона: какая задача, ответ, расход, итог |
| `results.jsonl` | строка на задачу: тип, reward, ответ, исход (`answer`, `unanswerable`, `precheck`, `coding_stuck`…), расход, вызовы, время |
| `calls.jsonl` | строка на вызов модели: входные, выходные и рассуждающие токены, стоимость, накопленный расход |
| `traj/<задача>.jsonl` | ответы модели и решения харнесса по шагам: запуск тестов, правки, повторы, остановки |
| `proxy.jsonl` | журнал прокси: каждый запрос, начало промпта, токены |
| `score.txt` | проверка ответов, баллы по типам, расход на невыполнимые, кривая «баллы от бюджета» |

## Что делает код и почему (для проверки безопасности)

| Что может насторожить | Где | Зачем |
| --- | --- | --- |
| Исполнение кода, который написала модель | `shell.py`, `solver.py`, `texttool.py` | так решаются math, data и fallback-поиск: Python запускается через `python -I` в каталоге задачи (таймаут 30 с), команды `sh` — с таймаутом 60 с. Из окружения подпроцессов удаляется `LLM_API_KEY` |
| Правка `.py` и запуск тестов | `coding.py` | это и есть coding-задача: харнесс вставляет правку модели в исходники задачи через AST и запускает видимые тесты. Файлы тестов не меняются |
| Сетевой клиент с ключом | `solver.py`, `_new_agent()` | запросы к модели идут только на `LLM_BASE_URL` из окружения через клиент openJiuwen, других адресов в коде нет |
| Загрузчик `.env` | `run_agent.py` | только для локальной разработки. `.dockerignore` пропускает в образ только `run_agent.py`, `budget_agent/` и `requirements.lock`, `.env` туда не попадает |
| `uv` и `compileall` в Dockerfile | `Dockerfile` | `uv` ставит зафиксированные пакеты при сборке и сразу удаляется. `compileall` заранее собирает байткод, потому что при запуске корень read-only |
| Перенос логов openJiuwen | `ojw_logging.py` | openJiuwen по умолчанию пишет в `./logs`, а `/app` read-only: логи уходят в `/tmp` |

Изоляции между задачами внутри контейнера нет: каталог задач общий, его ограничивает только контейнер организаторов.
